## 1. 一句话诊断

**平台骨架已经立住，产品血肉还没长。**

契约、几何、持久化、管理台这四件事做到了「能演示」；但「用户为什么要往桌面上放一个小组件」目前没有被回答——三个内置件里没有一个是可用的，管理面只能证明增删改查通了，不能证明桌面因此更有用。

拆成八个断点，每个都对应 §2.2 的证据与 §4 的设计（B1~B6 来自代码与实测走查，B7/B8 是 §4.0 拿 HIG 对照时补出来的）：

| #   | 断点                                                                                     | 证据               | 设计                 |
| --- | ---------------------------------------------------------------------------------------- | ------------------ | -------------------- |
| B1  | 小组件没有数据归属：交互结果不落库，删件即丢数据                                         | E1                 | §4.2                 |
| B2  | 内容与档位不匹配：卡片大片死白                                                           | E3                 | §4.4                 |
| B3  | 浅色主题下读不清，且件内没有「可读性地板」                                               | E4 E13             | §4.6                 |
| B4  | 契约字段有、产品里没有（`openAppId`/`keywords`/`pos` 空转，配置四类只走通一条）          | E5 E6 E7           | §4.5 §4.7 §4.8 §4.12 |
| B5  | 管理面只能「管记录」，不能「挑组件」（无描述、无预览、同一件列两遍）                     | E8                 | §4.8                 |
| B6  | 摆放不可控且看不见（不能排序、不能改位置、改尺寸只能翻菜单、溢出是黑箱、纵向还粘在一起） | E9 E10 E16 E17 E18 | §4.7                 |
| B7  | 下钻只到应用首页，不到具体内容（而 `useOS().open` 本来就收 payload）                     | E14                | §4.5                 |
| B8  | 展示件没有「为什么值得一直摆着」的答案：内容不变或价值等同一个图标                       | E15                | §4.9                 |

> 后两个断点不是新发现的代码问题，是**拿 Apple HIG 当尺子量出来的**（§4.0 H 组第 1、6 条）：前者是「点小组件应当落在与该内容直接相关的详情页，而不是让用户自己在 App 里导览」，后者是「内容似乎从不变化的小组件，用户不会把它放在显眼位置；复制 App 图标几乎不提供额外价值」。这两条把 §4.5 与 §4.9 从「我们觉得该这样做」升级为「有出处的规矩」。

## 2. 现状梳理

### 2.1 已经立住的部分（不重做）

| 层     | 落点                                                                                         | 状态 | 说明                                                                                                                            |
| ------ | -------------------------------------------------------------------------------------------- | ---- | ------------------------------------------------------------------------------------------------------------------------------- |
| 契约   | `kernel/stores/widgetRegistry.ts` `WidgetManifest`                                           | 完整 | 与 `AppManifest` 同构、刻意不进窗口体系；字段全可选，向后兼容                                                                   |
| 注册   | `main.ts` 第三条 glob + `register()` 按 `order` 稳定插入                                     | 完整 | 加目录即上架，不改壳层                                                                                                          |
| 实例态 | `kernel/stores/widgets.ts`（IDB `widgets-v1` / `widget-kinds-v1`）                           | 完整 | 增删/换尺寸/改配置/安装/启用/卸载 + 容错式恢复 + `snapshot()` 剥代理                                                            |
| 几何   | `kernel/widget/geometry.ts`                                                                  | 完整 | 纯函数、右锚定、band 流式、overflow 不静默裁剪，13 例单测覆盖算术（**但其中一条把「纵向零间距」断言成了正确行为**，见 E17）     |
| 渲染   | `WidgetLayer` → `WidgetFrame` → 组件                                                         | 完整 | 材质单点、prop-less 上下文、Suspense 骨架 + `ErrorBoundary`（骨架已是「不同宽度矩形」形态，与 HIG 占位符建议同构，见 §4.0 A-6） |
| 管理面 | `components/WidgetConsole.vue`（抽屉 + 小组件中心两个外壳）                                  | 半   | 功能通，信息架构不对（见 B5）                                                                                                   |
| 内容   | `src/widgets/{clock,calendar,todos}`                                                         | 缺   | 三件都是占位演示（见 B1/B2/B3）                                                                                                 |
| 质量线 | 单测 5 文件 / e2e 8 条（`widget.spec.ts`）/ 视觉 4 张含小组件 / a11y 9 个场景里小组件占 3 个 | 半   | 覆盖面是「机制」，不是「功能」（见 §9）                                                                                         |

结论：**该收敛的机制都收敛了，该长出来的功能一根没长。** 所以补齐不能靠再改一遍平台层数据结构，而要往「内容 + 数据 + 摆放 + 挑选 + 下钻」五个方向长。

### 2.2 断点证据（E1~E18）

**E1 · 待办的勾选状态刷新即丢。** `src/widgets/todos/App.vue:22` 的 `done = ref([true,false,false])` 是组件内状态。实测：勾选第二项 → 划线生效 → 刷新 → 回到未勾（而实例的**配置**是落 IDB 的）。也就是说：系统里唯一「可交互」的小组件，交互结果哪儿都不去。附带两个同源问题——清单内容是硬编码三条演示文案（`:12`），既不能增删改，也没有归属应用（全仓库没有「待办」应用，删掉这个件，数据无处可寻）。

**E2 · 月历不能翻月。** `calendar/App.vue` 全文只渲染「当前月」，60 秒重绘一次；没有左右翻页、没有点选日期、没有「回今天」、没有日程。而《开发指南》§7 写着「交互件（如待办勾选、**月历翻月**）」——文档口径与实现不符。

**E3 · 内容填不满卡片（实测）。**

| 件   | 档位 | 卡片尺寸  | 实测内容止于                     | 死白                            |
| ---- | ---- | --------- | -------------------------------- | ------------------------------- |
| 月历 | lg   | 344 × 344 | 最后一行日期 y=428               | **144px / 41.9%** 在底部        |
| 待办 | md   | 344 × 160 | 最后一条 li 底部                 | **54px / 34%** 在底部           |
| 时钟 | md   | 344 × 160 | 时间墨迹宽 97px、日期墨迹宽 87px | 可用宽 310px，横向占用 **≈31%** |

月历声明「只有 lg」（`sizes: ['lg']`）思路是对的——问题不在档位选择，在于 **lg 档里没有第二层内容**（日程/农历/周视图任选其一都能填掉那 144px）。

**E4 · 浅色主题下前景不可读（实测 + 算术）。** `WidgetFrame.vue:104` 硬编码 `text-white`，而卡片底色跟着主题翻：

- 深色主题：`--raw-glass-bar: rgba(30,41,59,.55)` → 白字没问题。
- 浅色主题：`--raw-glass-bar: rgba(255,255,255,.28)`，叠在 `wallpaper-sky` 上。该壁纸自上而下 `#6ea8e0 → #9cc4ec → #cfe3f6 → #e6f0f9`，白字对比度分别约 **2.49 : 1 / 1.82 : 1 / 1.29 : 1 / 1.15 : 1**（WCAG AA：正文 4.5、大字 3.0）——这已是**未计入**卡片自身 28% 白玻璃再抬亮底色后的乐观读数，实际更低。小组件右锚定且向下铺，月历最后两行正好落在壁纸最亮的那一段——`shell-light.png` 基线里那两行肉眼可见地淡出，与此吻合。

现有门禁抓不到它：`contrast.spec.ts` 只算语义 token 的派生对，`a11y.spec.ts` 的 axe 扫的是抽屉/中心/菜单三个弹层，**桌面卡片不在任何对比度断言里**（axe 也无法穿透 `backdrop-filter` 解析背景）。

**E5 · `openAppId` 零内置件使用。** 全仓库该字段只出现在：契约定义、`WidgetFrame` 消费、单测造数据。产品里没有一个件是「点开进应用」的——因为**根本没有对应的应用**（没有日历、没有待办、没有时钟应用）。一个已经写进《开发指南》§7 的交互契约，在真实桌面上从未被走过。

**E6 · 配置面形同虚设。** 契约支持 `text/number/boolean/select` 四类，内置件只用了 1 个 boolean（`clock.hour12`）。深看一层：`select` 的 `options` 是裸字符串（`WidgetConsole.vue:179` 直接 `label: o`），双语下要么显示英文原值、要么把中文塞进代码，且**绕过 i18n 齐平门禁**；`number` 无 min/max/step，`text` 无校验；文本框每次 `update` 都走 `updateConfig → persist`，**每个击键一次 IDB 写**（`widgets.ts` 无防抖，与 windowManager 的 400ms 防抖不同口径）。

**E7 · 三处「预留即死数据」。** `WidgetInstance.pos` 恒为 `null`（无任何写入方）；`manifest.keywords` 注释自陈「预留：小组件库搜索」而管理台没有搜索框；`WidgetFrame` 挂了 `cq-widget` 容器根但「刻意未定义变体」。预留字段本身不是问题，**没有排期的预留**才是半成品感的来源。

**E8 · 管理台只能管记录，不能挑组件。** 目录行只有图标 + 名称 + 开关（`WidgetManifest` 根本没有 `description` 字段）；没有预览，用户无法在添加前知道它长什么样、sm/md/lg 各能放下什么。同时同一个 kind 在两段各出现一次，**两处都有「尺寸」分段控件而语义不同**（实例段＝当前档，目录段＝待添加档）——`widget-gallery.png` 里「时钟」出现两遍、两个尺寸选择器，就是这个 IA 问题的直接成像。

**E9 · 溢出是黑箱。** 右下角只有「+N 个未显示」，不说是哪些件、不给处置动作；用户唯一的解法是移除别的件或放大窗口。管理台实例行也不标「这个件其实没在桌面上显示」。

**E10 · 窗口一开，小组件就没了。** 小组件层 `z-desktop=5`，在窗口之下（e2e 已断言）；窗口默认级联落位从 `bounds.x + 140` 起（`windowManager.ts:100`），正是右锚定 band 的位置。开两个窗口后桌面件基本永久不可见，而系统里**没有任何「速览桌面」的出口**（无「显示桌面」、无临时提层）。

**E11 · 没有生命周期与调度契约。** 时钟每实例自持 `setInterval(1000)`、月历每实例 `setInterval(60_000)`：加两个时钟实例就多一个定时器，页面隐藏不暂停，宿主也不告诉组件「你被溢出了 / 被停用了 / 不可见」。数据型件需要的「刷新节奏 / 立即刷新 / 上次更新时间」概念在契约里完全不存在。

**E12 · 生成器只出占位。** `gen-widget` 产出的 `App.vue` 内容就是 `size · config JSON` 调试文本，放到桌面就是一张写着 JSON 的卡；不生成 `config` schema、不生成 `nameKey`、不写语言包两份。所以「照指南第 1 步上手」的第一个结果是一个**单语 + 调试内容**的半成品件。（同样问题在 `gen-app` 也存在，属生成器工作线，不是小组件独有。）

**E13 · 件内文字没有地板。** 月历星期表头用 `text-micro`（`calendar/App.vue:38`），而 `--text-micro: 10px`（`tokens.css:17`）——同处还叠了 `opacity-70`：最小字号 × 半透明前景，正好落在浅色壁纸最亮那一段（与 E4 同一位置）。对照 HIG「一般而言使用 11 点或更大字号，字体小于 11 点的文本对许多用户都很难看清」，这行是**违规的**。（`todos/App.vue:40` 的勾选框字形也用 `text-micro`，但那是符号渲染尺寸，不是文字可读性，不受地板约束。）

**E14 · 下钻机制只走了一半。** `WidgetFrame.vue:46` 是 `os.open(target)`——只给 appId；而 `useOS.ts:15` 的签名是 `open(appId, payload?)`，窗口侧早已把 payload 透传给应用。也就是说「深链到具体内容」**平台层已经备好，小组件契约没接上、应用侧消费没约定**。这不是「缺功能」，是三层里缺了中间那层的字段（因此成本远低于新增下钻能力本身）。

**E15 · 「值得一直摆着」这件事没有被判过。** 现有 3 件按时序看：时钟每秒变（合格）、月历每天变一次（勉强）、待办除非用户操作否则永不变（靠交互而非内容维持价值）。批次 C 草稿里「我的网页应用」的内容是 **Dock 已有图标的子集**、「AI 助手入口」若按初稿就是一个开应用的按钮——按 HIG「复制 App 图标几乎提供不了任何额外价值，用户可能不会将其保留在屏幕上」直接判为**低价值件**。此前没有任何一条判据把「它会变吗 / 它比图标多给了什么」列为准入条件（§4.9 现在补上）。

**E16 · 「改大小」的能力在，手势不在。** 机制侧其实已经跑通：`store.setSize()` 落 IDB、reload 仍在（`widget.spec.ts` 已断言「按尺寸添加并刷新仍在」），卡片菜单与管理面分段控件都能切档。缺的只有**直接操作入口**（当时的结论是「补一个拖角手势」；入口后来确实先做成拖角，2026-10-07 又被用户判为重复并撤掉，见偏差 29）。更深一层是几何算法的边界：`packRight()` 的入参是 `{ id, size }`（`geometry.ts:78`），band 内排布硬编码了两条假设——`sm` 两两配对占满一行（`halfUsed` 状态机）、`md/lg` 独占整行（`:108` 的 `item.size !== 'sm' && halfUsed` 分支）。**结论：吸附到「已声明档」是零几何改动（换 size 值即可）；要任意 span 就得把 packer 重写成占用网格模型**——这是本方案里最贵的一条分界线，也决定了 §4.7 的分期。

**E17 · 纵向没有间距，卡片是粘在一起的。** `packRight()` 只在**横向**算过 gutter：band 与 band 之间 `pitch = bandW + gutter`（`geometry.ts:87`）、两个 sm 并排时 `bandLeft + cell + gutter`（`:117`）。而**行推进三处全部只加卡片高度、不加 gutter**——`rowY += smH`（`:110`）、`rowY += span.h`（`:125`、`:130`）。于是同一 band 内上下相邻两件净间距＝**0px**，桌面实测（用户截图 2026-10-06）时钟卡与月历卡边缘直接相接，两张玻璃卡糊成一张大玻璃。连带两个后果：① 材质层失效——`WidgetFrame` 的 `shadow-dock` 投在邻居身上，「一张件」的边界读不出来；② `gridH` 的溢出判定（`:113`）按无间隙累计，**同一 band 能塞下的行数比设计意图多**（余量恰好吃掉 gutter 时才会显形，见附之三），补间距后除零间距消失外，**每张卡片的 y 还会整体下移**（累计 gutter）→ 视觉基线连带红，属可预期的一次性重生成（G-3、§5 连带门禁）。横向 24px、纵向 0px 不是取舍，是漏写。更深一层的坏处在门禁侧：`tests/unit/widget-geometry.test.ts:93-96` 断言 `sm→md` 两件的 y 为 `68` 与 `228`（`68+160=228`，间隙恰为 0），**现有单测把零间距写成了期望值**——所以这条永远不会红，只能靠眼睛发现。

**E18 · 摆放域没有左界，第三 band 会压住壁纸标语。** 标语块固定在 `left-12 top-[36%]`（`Desktop.vue:43`），主句字号 `--text-display-1: 48px`（`tokens.css:33`）——「Atrium OS」实测（2026-10-07，STKaiti 48px）≈153px 宽，右缘约 x=201。而网格右锚定且**随视口变宽向左扩**：1280 视口下 `cols=13`、`gridW=1172`、`originX=84`（算术见附之三），第三 band 左缘落在 x=176，**已经进入标语区**；`WidgetLayer` 在 `Desktop` 之后渲染（`App.vue:35/38`），压上去就是撞字。今天 3 件（1 个 band）看不见它，但 §4.9 批次 B 之后桌面会有 8~10 件——**这条会在 P1 结束时自己撞出来**。所以摆放要么有左界，要么标语让位（§4.7 末段、决策 12）。

### 2.3 能力矩阵

| 能力域         | 平台已给 | 产品可用 | 缺口一句话                                                               |
| -------------- | -------- | -------- | ------------------------------------------------------------------------ |
| 注册与契约     | ●        | ●        | 缺 `description`、`refresh`、下钻 payload                                |
| 实例增删改     | ●        | ●        | 配置控件的 i18n/校验/防抖                                                |
| 种类生命周期   | ●        | ●        | 实例粒度启用（挂账，见 §8 末段「继续挂账」）                             |
| 几何与排布     | ●        | ◐        | 顺序不可控、无拖拽、改尺寸无手势入口、溢出黑箱、纵向零间距、摆放域无左界 |
| 数据归属       | ○        | ○        | **整域缺失**                                                             |
| 时间与刷新     | ○        | ○        | **整域缺失**                                                             |
| 下钻与深链     | ◐        | ○        | `open` 收 payload，件侧只给 appId（B7/E14）                              |
| 表面与主题     | ◐        | ○        | 浅色不可读、无字号地板（B3/E13）                                         |
| 内容（内置件） | ◐        | ○        | 3 件皆占位，档位与内容不匹配                                             |

**用户视角**

- **U1 有东西可放**：内置件 ≥ 8 个，覆盖**时间 / 日程 / 任务 / 笔记 / 系统状态 / 快捷设置 / 文件**七类（批次 A 的 3 件 + 批次 B 的 5 件即达标，不依赖批次 C）。第八类「入口」（一键拉起常用应用）**从判据里撤掉**：按 E15 与 HIG，纯入口件的内容是 Dock 已有图标的子集，价值最低，不该拿来当「桌面因此更有用」的证据。

**开发者视角（K 组）**

- **K1 只动一个目录**（已达成）+ 生成器产出**可直接上线**的骨架（双语 key、真实内容分区、无调试文本）。

### 4.1 分层与职责

补齐后的小组件体系分三层，各层只对自己的东西负责：

| 层       | 负责                                                     | 落点                                        |
| -------- | -------------------------------------------------------- | ------------------------------------------- |
| 平台层   | 契约、注册、实例态、几何、渲染、调度、表面、持久化写边界 | `kernel/`、`shell/Widget*`                  |
| 内容层   | 每个件「放什么内容、每档怎么排、能点什么、数据长什么样」 | `src/widgets/<id>/`                         |
| 管理面层 | 挑组件、摆放、配置、生命周期、溢出与孤儿数据治理         | `components/WidgetConsole.vue` + 小组件中心 |

本文 §4.2~§4.7 是平台层的补齐，§4.8 是管理面层，§4.9 是内容层，§4.12 是配置面归属。

**「高内聚低耦合」在这条线上是可检查的，不是一句口号**。它有两个方向的判据：

- **内聚**＝一件功能只在一个地方被决定：内容归 `src/widgets/<id>/` 一个目录、材质归 `WidgetFrame` 一处、写边界归 `widgets.ts` 一处、调度归宿主一处（§4.3）、「这件该放什么」归 §4.9 一张表。
- **低耦合**＝跨层只走**声明过的通道**（manifest 字段、`useWidgetContext`/`useWidgetData` 这类 composable、CommandBus、VFS），不走彼此的实现细节（禁 import 别的件、禁件内直连 store、禁壳层认识某个件的业务）。

按这两个判据盘点，补齐后**仍然会留下 5 处刻意耦合**——它们不是疏忽，是换来的能力，但必须登记在册、各带护栏，否则下一个人会误以为「耦合可以随便加」：

| #   | 跨层耦合点                                                  | 换到了什么                                                  | 护栏（越界即评审否决）                                                                                                                 | 可撤销性                           |
| --- | ----------------------------------------------------------- | ----------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------- |
| C-① | 管理面/预览沙箱直接渲染 `manifest.entry`                    | 「添加前就看得见真实长相」（HIG A-5，解 B5/E8）             | `pointer-events:none` + `aria-hidden` + 标「预览」；件必须在 mock context 下可渲染，且数据/写/调度三通道在沙箱内被屏蔽（§4.8、T6）     | 可退成静态图版，代价是 B5 复发     |
| C-② | `useWidgetData` 把 VFS 路径约定写进平台层                   | 删件不丢数据、数据在文件管理可见、可被别的应用消费（解 B1） | 路径模板只此一处；件不得自己拼路径；孤儿数据有出口（§4.2）                                                                             | 可把寻址交回件，代价是暗仓化       |
| C-③ | 待办件与「今日」应用共享同一份 `tasks.json`                 | 数据有归属、下钻有落点（U2/U7）                             | **用数据契约替代组件耦合**：两边互不 import，只共享 schema 与文件；schema 变更走一次迁移                                               | 结构性，撤销＝回到「件即唯一副本」 |
| C-④ | 首次拖拽/改尺寸把**全部**实例的 `pos`/`size` 固化成网格坐标 | 用户摆的位置在视口变化后仍是他摆的（解 B6）                 | 一次性迁移、无 IDB 版本变更；`pos=null` 语义永久保留（自动流式仍是缺省态）；固化的是 `{col,row}` 而非像素（L-1）                       | 可撤销（清 `pos` 即回自动流式）    |
| C-⑤ | 件可提供 `configEntry` 自绘配置面板（§4.12）                | 复杂配置的表达力（时区搜索、分组、联动）                    | schema **仍必填且仍是写边界**：未声明键被 `sanitizeConfig` 丢弃；面板容器与材质归宿主；`Config.vue` 禁 import `kernel/stores/*`（T12） | 可不声明，退回宿主默认渲染         |

> 台账的用法：新增任何一条跨层引用，先在这里登记（换到什么 / 护栏 / 能否撤销），登不出来就说明它是耦合而不是代价。

### 4.2 数据契约（解 B1）

**数据三分法**——先划清归属，再谈 API：

| 数据                                          | 归谁     | 落点                                | 生命周期                     |
| --------------------------------------------- | -------- | ----------------------------------- | ---------------------------- |
| 平台状态（实例/尺寸/顺序/配置/kind 生命周期） | 平台     | IDB `widgets-v1`、`widget-kinds-v1` | 已有，不动                   |
| 小组件自有业务数据（任务、便签、日程）        | **VFS**  | `/我的数据/<key>.json`              | **与实例解耦：删件不删数据** |
| 系统状态（主题、语言、通知、文件、网页应用）  | 各 store | 已有                                | 只读或经 store 动作写        |

为什么走 VFS 而不是新开一个 IDB 键：纯前端约束下 VFS 就是本项目唯一的业务数据后端（S4 的 `vfsDataSource` 已在 file-manager / data-board 用过），走 VFS 让小组件的数据**在文件管理里可见、可被别的应用消费、可导出**——小组件因此是「视图」而不是「数据唯一副本」。这也是 U2 后半句的实现前提。

**契约**：`useWidgetData<T>(key, factory)`，由宿主提供，返回

```
{ data, write(next), patch(partial), status: 'idle'|'pending'|'error', retry() }
```

规则（写进指南，不让每个作者重踩）：

1. **寻址**：共享数据 `/我的数据/<key>.json`；实例私有数据 `/我的数据/<kindId>/<instanceId>.json`（组件不拼路径，宿主按 context 里的 `instanceId` 拼）。
2. **乐观更新 + 失败回滚 + 通知中心上报**——沿用 S3/S4 已确立的三态与集中上报口径，不在件内弹错误框。
3. **写边界统一**：落库前 `snapshot()` 剥代理（S14 的 `DataCloneError` 教训）、300ms 防抖合并（同时解 E6 的每击键一写）。取 300 而非沿用 windowManager 的 400：那边合并的是几何写回，这边对齐的是输入停顿，两个值各属自己的子系统，不强行统一成一个「全局防抖常量」。合并的键是**路径**而不是 handle——同一份 `shared` 数据允许多个写者，挂起值必须按 VFS 路径共享，否则窗口内的后一次写会吃掉前一次（回写后定稿，见 §8 偏差 16）。
4. **首次读给 factory 默认值并落盘**，避免「空」与「未初始化」两种状态在组件里纠缠。
5. **删件不删数据**；孤儿数据（`/我的数据/` 下已无实例引用）在小组件中心给一个「数据」段列出来，附「清除」。（P2）
6. **kind id 一经发布就是数据键，不得重命名**：`widgets-v1` 的实例与 `widget-kinds-v1` 的安装/启用状态都以 kind id 为键，改名等于让用户桌面上那个件连同状态一起消失（表现为「我没删它，它自己没了」）。要改口径改 `name`/`nameKey`——所以批次 A 的「今日待办」**仍叫 `todos`**，只有显示名变。（进 §8 指南禁止事项）

**连带决策**：任务/日程需要一个「家」。推荐开一个最小应用 **「今日」**（清单 + 日程，VFS 背书，见 §6 决策 3）——它同时解决三件事：删件后数据有归属、`openAppId` 第一次被真实消费（E5）、月历的 lg 档有第二层内容可填（E3）。

### 4.3 时间与刷新契约（补 E11）

- **`useWidgetTick(ms)`**：宿主级**共享调度器**（一个分发器 + 多订阅），带 `document.visibilitychange` 暂停；组件卸载自动退订。**组件内禁止自持 `setInterval`**（写进指南 §10 禁止事项）。
- 建议节奏档（与 `refresh` 枚举一一对应，不另立一套名）：`live`→`1s`（秒针）与 `30s`（时钟分钟、相对时间）；`minute`→`5min`（系统状态）；`hour`→`1h`（存储）；`day`（日程）；`manual` 不注册调度、只响应「立即刷新」。
- **`manifest.refresh?: 'live' | 'minute' | 'hour' | 'day' | 'manual'`**：宿主据此在卡片右键菜单给「立即刷新」，并向组件暴露 `useWidgetStatus().lastRefreshAt`，件内可显示「更新于 x 分钟前」。无数据源的件不声明。
- **(HIG) A-9 的「上次更新时间」由宿主出一个 composable**（`useWidgetUpdated()` → `ComputedRef<string>`，`src/kernel/composables/useWidgetUpdated.ts`）：相对时间走 `Intl.RelativeTimeFormat`（`src/kernel/relativeTime.ts` 的 `relativeTimeLabel`，语言包只留「更新于 {time}」这一层包装语，不再手写 `x 分钟前 / x 小时前` 四个复数叶子），取不到 `lastRefreshAt` 时回落到 setup 时刻——**这条回落是 A-13 预览同构的前提**：预览不取数、不刷盘，若读数只在异步 fetch 之后才有，桌面会比预览晚一帧多一行，T6 就成了自证。落位随档位的 R1 预算走（见偏差 17），不是统一一张卡底部一行。
- `useWidgetStatus()` 同时给出 `visible | overflow | disabled`——件据此决定是否暂停取数（被溢出时不该继续拉数据）。

### 4.4 尺寸与内容契约（解 B2）

档位与几何**不动**（`sm 2×2 / md 4×2 / lg 4×4`，cell 68 / gutter 24 是反解出来的，改它等于重做排布；H-7 只动**内边距**，网格跨列跨行不变）。要动的是「件声明档位的规矩」：

**可用内容区算术**（卡片尺寸 − 内边距 ×2 − 边框 1×2）。内边距目前只有 `p-md` 16 一档；按 (HIG)「标准外边距 16 点、需要分组时 11 点，且 **Mac 桌面使用较小的外边距**」补一档 compact（H-7、决策 8），两套数都列出来，取舍留给拍板：

| 档  | 卡片    | 内容区（default 16） | 内容区（compact 11）   | 容量直觉                                |
| --- | ------- | -------------------- | ---------------------- | --------------------------------------- |
| sm  | 160×160 | **126×126**          | 136×136（面积 +16.5%） | 一个数字 + 一行标签；或 2×2 图标 + 计数 |
| md  | 344×160 | **310×126**          | 320×136                | 标题 + 3~4 行列表；或 主数字 + 3 段条   |
| lg  | 344×344 | **310×310**          | 320×320                | 标题 + 6~8 行列表；或 网格 + 第二层内容 |

四条规则：

- **R1 每档都要有内容预算**：manifest 声明的每一个档，都要在 §4.9 的表里写清「放什么、放几行、放不下怎么办」。没有预算表就不许开那一档。(HIG：档位是「同一理念随尺寸层层扩展」，不是换一套内容 A-2)
- **R2 宁缺不夹生**：填不满的档不要声明（月历只声明填得满的档）。(HIG：「避免单为填充更大区域而扩展较小尺寸的内容」A-3)
- **R3 溢出走截断 + 计数出口，不滚动**：「还有 5 项」是链接语义，桌面件没有滚动条语义。
- **R4 密度有上界**（新增，HIG H-4：「布局稀疏显得多余，而布局过于紧密则不够简单明了」+「注意目标的大小，确保用户可轻松轻点而不会意外执行非预期的交互」）：
  - **每档交互目标上限**：`sm` 1 个、`md` 2 个、`lg` 4 个。超出就是把小组件做成迷你 App（HIG A-12「将复杂功能留给 App」）。
    **计数单位由 2026-10-06 评审定下（此前无数，是偏差 3 悬着的真正原因）**：一个「目标」＝一个**决定**，不是一枚按钮。同一决定的互斥选项（segmented 一排 chip、`aria-pressed` 的日格单选）合计一个；「一行一个独立决定」的列表型正文（待办每行勾选、最近文件每行打开）**不按个数计，按行数上限封**。定了这个单位，`md` 2 这条数值判据只约束「并列的独立控件」，不约束列表与配置面——它守的是「 glanceable 卡片被做成遥控器」，而不是「一屏上有几个 DOM 控件」。
  - **命中区 ≥ 24×24**：这条地板**只约束件内目标**——宿主已不在卡片表面自绘任何控件（诊断时点那颗「移除」按钮是 `h-5 w-5`＝20px、低于地板，本线先收敛为 `h-6 w-6`＝24×24，2026-10-07 再连按钮带拖角手柄一并从卡片上摘掉：移除改走右键菜单与 `Delete`，换尺寸改走菜单档位组与 `⌥←/⌥→`，见 §8 偏差 29；附之二那条 20×20 是快照读数，不就地改）。这条不靠肉眼——`readCards()` 的 `targets` 按选择器从卡片子树里取，T4 的每档命中区断言**没有豁免表**；而「展示型四件量到 0 个目标」与「其余六件必须量到」按 `DISPLAY_ONLY_KINDS`分岔，名单来自 §4.9 的件形态声明、不跟着测量结果走。**这条分岔是摘浮标时才暴露的**：原先那个 `> 0` 守卫对四个纯展示件也恒成立，靠的正是卡片上必然存在的那颗浮标——它从来没有守过件内取样。
  - **每档行数上限**：`sm` 2 行、`md` 4 行、`lg` 8 行——与 R1 的内容预算同表核对，超行按 R3 截断而不是缩行高（缩行高会连带踩 §4.6 的字号地板）。同一份评审把数法定了：**数的是 R1 预算里的正文行**，宿主层的标题行与「就地新增」行不计入（否则 §4.9 给待办 lg 的 8 行清单预算自身就超线，而那条预算是批次 A 逐条批过的）。

按此重排三个内置件（详规见 §4.9）：月历补 `md`（紧凑月网格）与 `lg`（月网格 + 当日日程）；时钟拉开三档差异（sm 只有时间、md 加日期行、lg 再加第二时区行）；待办在 md 显示「进度 + 前 4 条 + 还有 N 项」、lg 显示完整清单 + 就地新增。

**验收**：结构断言 T2——每档实测「内容包围盒 / 卡片内框」，连续死白 ≤ 15%（U4）。R4 的三项上限**不进自动化**（测不出「设计上太挤」这种语义），改为 §4.9 表逐条人工核对 + 评审时对照；只有命中区尺寸可静态测（组件树里按钮的 `getBoundingClientRect`），并入 T4。**但命中区那条腿必须量最差形态，不能只量默认屏**（2026-10-06 补，见偏差 20）：行数上限本身不自动化，可它决定的**内容体积**会把行高由 `minmax(0,1fr)` 倒推出来的格子压到地板以下——那正是「不自动化的数字」咬到「自动化的地板」的接缝。所以 T4 另有两条以行预算为输入的最差形态腿（月历·lg 6 行月 + 议程满、待办·lg `config.limit` 配到 schema 上界），各自先断言那一屏确实是最差形态再量格子，防止上界没量到而腿自绿。

### 4.5 交互契约（解 B4 的点击半边）

件分三类，语义互斥，写进指南：

| 类型   | 定义                 | 平台行为                                         | 例                   |
| ------ | -------------------- | ------------------------------------------------ | -------------------- |
| 展示型 | 无内部交互           | `openAppId` 生效，整块可点、光标 pointer         | 存储用量、数据摘要   |
| 交互型 | 卡内自持交互         | 平台不接管点击；**标题行由组件自己做成下钻入口** | 待办、便签、快捷设置 |
| 混合型 | 有交互又有主下钻目标 | 同交互型，另在卡片菜单给「打开 <应用>」          | 月历（点日期看日程） |

> **与 (HIG) 的默认方向差一条，已想清楚怎么变形采纳**（H-8）：HIG 的默认是「除按钮/切换外的区域轻点即启动 App」，我们的机制是「不声明 `openAppId` 就不接管点击」。**机制保持不变**（桌面 Web 用鼠标、误点代价与触屏不同；交互件需要自己的完整点击域），**语义靠纪律补平**：每个内置件都必须回答下钻问题（第 3 件事），所以用户在任何一张卡上的体验都是「点空白处就进到该看的地方」——与 HIG 的默认一致。

平台要补的四件事：

1. **卡片菜单加「配置…」项**：现在改配置要走「管理小组件…」→ 开窗口 → 在列表里找到那一行，路径太长。补一项直接打开抽屉并**滚动 + 高亮到该实例**（`shellUi` 加 `focusInstance(id)`）。面板本体归 §4.12：宿主给容器与草稿/提交通道，件可按 schema 缺省渲染或声明 `configEntry` 自绘。
2. **下钻可达性判定**：`openAppId` 指向的应用若当前会话不可访问（`session.canAccess`），整块点击与菜单项都要**自动消失**——现在只判了 kind 可见性，没判下钻目标。
3. **下钻要带 payload，落在具体内容上**（新增，(HIG) H-1：「深度链接至与小组件内容直接相关的详细信息和操作，而不应让用户自行导览至 App 中的相关区域」）。现状：`WidgetFrame.vue:46` 只 `os.open(target)`，而 `useOS().open(appId, payload?)` 早就支持透传（E14）——**三层里只缺件侧那一层的字段**。改法：`openAppId` 从 `string` 扩为 `string | { appId: string; payloadFor?(ctx): unknown }`，`ctx` 给 `{ size, config, selected }`（月历给选中日期、待办给未完成筛选、最近文件给节点路径）。**验收口径**：内置件的下钻**必答题**答满（声明落点或写明豁免理由），且件必须声明「点下去落在哪」这句话，答不出又不豁免的件不进 §4.9（决策 7、T5）。
4. **动作反馈分级**：勾选/切换这类可逆动作**不弹确认**（桌面件要随手可用）；删除条目弹一次确认（与「移除件」同口径）；失败走通知中心。撤销（undo）等通知中心支持 action 按钮后再做，不提前设计。

**键盘路径**（补 a11y）：卡片本体 `tabindex=0`（现在只有内部控件可达），聚焦后 Enter＝下钻/打开应用、`Delete`＝移除（走确认）、`⌘]`/`⌘[`＝在桌面序列里前后移一格（依赖 §4.7 的顺序可控）、`⌥←`/`⌥→`＝在前一/后一尺寸档间切换（换档的键盘等价物，§4.7 S-6；2026-10-07 起它同时是换档的**唯一直接操作**入口之一，另一个是卡片菜单档位组）、`⌘⇧←/→/↑/↓`＝按格挪动（拖拽摆放的键盘等价物，§4.7 L-6）。键盘等价物不只约束卡片级手势：件内**悬停才显形**的控件（待办行尾的删除钮这类 `opacity-0 group-hover:opacity-100`）必须同时挂 `group-focus-within`，否则它只对鼠标存在；判据在 T4（量 computed opacity，`toBeVisible()` 测不出——Playwright 的可见性只看盒子与 `visibility`，`opacity: 0` 照样判定可点）。

### 4.6 表面与主题契约（解 B3）

**根因**：前景硬编码 `text-white`，表面跟着主题翻。两者必须同源。

**方案（推荐，见 §6 决策 1）**：新增「小组件表面」token 层，卡片前景与表面**同层派生**，组件不再触碰颜色：

```
/* tokens.css 新增，明暗各一档 */
--color-widget-surface        /* 卡片底 */
--color-widget-ink            /* 主前景 */
--color-widget-ink-mute       /* 次级前景（替代现在混用的 opacity-70/80/90） */
--color-widget-ink-disabled   /* 禁用/已完成（替代 opacity-50） */
--color-widget-line           /* 件内分隔 */
--color-widget-fill           /* 件内浅底（chip、进度槽） */
```

取值原则：**卡片必须自带可读底**，不能把可读性外包给壁纸。浅色档 surface 取 `rgba(255,255,255,.72)`（比 `glass-bar` 实一档）配 `--raw-ink`；深色档 surface 取 `rgba(30,41,59,.62)` 配 `--raw-ink`。`backdrop-blur` 保留，但它只负责质感，不再负责可读性。

配套约束：

- `WidgetFrame` 只负责 surface / border / shadow / radius / `color: var(--color-widget-ink)`；**组件内禁止 `text-white`、禁止对前景用裸 `opacity-*`**（这两条正是 E4 的两个来源）。(HIG) 的直接口径：虚化渲染「使用不透明的灰度值而非白色的不透明度」——把三级前景做成三档**不透明** token，比四个透明度类叠加更难写错（A-8）。
- **文字地板**（新增，(HIG) H-2）：件内**文字**一律 ≥11px，也就是 `--text-micro`（10px）在 `src/widgets/` 下**禁用**；符号（`OsIcon` 的 `:size`）与图形不受限。现状唯一违规点就是月历星期表头（E13），改 `text-caption`（12px）即可——注意它会挤压 7 列宽度，正是 §4.4 R4「不要靠缩行高/字号塞内容」的具象。
- **不得只靠颜色传达含义**（新增，(HIG) H-3：「在传达含义时不要依赖特定颜色…除了颜色外，另外使用文本和图示表达含义」）：进度环、在线/离线点、涨跌、已完成，必须**同时**有文本或图形通道（百分比数字、勾形、图标形状）。批次 B 的存储用量与系统状态首当其冲。
- 卡片自带底 + `backdrop-blur` 只负责质感，因此前景配色与壁纸**解耦**：这也是 (HIG)「为文本和背景使用具有语义的颜色，让颜色动态适配当前外观」的 Web 版落地（A-7）。
- 验收 T3：两套主题 × 三张壁纸 × 每档，逐件断言 computed `color` 与 `--color-widget-surface` 解析后的对比度（**算 token 层，不穿透 `backdrop-filter`**——穿透了就测不出漂移），并同批断言件内文字 `font-size` ≥ 11px。

### 4.7 摆放、尺寸与可见性（解 B6）

本节先立**一条地板（间距）**再排**四步**：地板不是排期问题，是漏写（E17）；四步的顺序按 §2.2 E16 的几何分界线排，不按直觉排。

**排布间距契约（G-1…G-3，解 E17，落 P0）**

| #   | 规则                                                                       | 为什么                                                                                                                                                |
| --- | -------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| G-1 | **任何两件（含同 band 上下、跨 band 左右）净间距恰好＝`GUTTER`，不得为 0** | 行推进补 gutter 即可（`geometry.ts:110/125/130` 三处 `rowY += h` → `rowY += h + gutter`）；横向已经是这个值，纵向没理由例外                           |
| G-2 | 间距是**平台常量**，件侧不声明、不可配置                                   | 与 `CELL/MARGIN` 同族；一旦允许件自定间距，U5 的「齐」就没了权威                                                                                      |
| G-3 | 补间距后**重算溢出判定**（`:113` 的累计含 gutter），并一次性重生成视觉基线 | 现状按无间隙累计，行数上限偏大（余量恰好吃掉 gutter 时才显形，逐档算过，见附之三）；且修完第二行往下 y 整体 +24/+48，基线必然重生成——预期内连带（§5） |

四步：

1. **P0 顺序可控**：把「桌面顺序」的权威从 `addedAt` 改成 `items` 数组下标（`renderable` 的排序键换掉，`addedAt` 退为创建时间戳），管理台实例行给上移/下移 + 列表内拖拽。**这一步解决 80% 的「我想要的顺序不对」，成本约为拖拽摆放（第 4 步）的 1/5。**
2. **P1 改尺寸（离散档位）**：换档的落点是**该 kind 已声明的档**，入口给两个——卡片菜单的档位组（多档才出）与键盘 `⌥←/⌥→`。这一条看着比拖拽「更大」，实际更便宜（E16）：`setSize()` 的落库、恢复、右键菜单档位条目全是现成的。**当初按「右下角手柄拖动 + 吸附」实现过，2026-10-07 用户拍板把拖角从卡片表面撤掉（理由：右键菜单已经满足，浮标是重复入口）**，规格见下面「尺寸的硬规则（S-1…S-6）」。
3. **P1 溢出治理**：`+N` 从「数字」升级为「可展开的未显示清单」——每行给件名、当前档、**成因**（`no-space`/`out-of-range`/`collision`）、三个动作（换小一档 / 移除 / **在管理台定位**：带实例 id 开抽屉，那一行展开配置面板并滚进视线）；管理台实例行标「未在桌面显示」。
4. **P2 网格吸附摆放**：`pos` 落地，但**落的是网格坐标，不是像素**。拖到空位、吸附到格、不许重叠——「想放哪就放哪」在桌面这种无框画布上只会把桌面变成堆杂物，用户要的是「我摆的位置」而不是「任意的位置」。规格见下面「拖拽摆放的十条硬规则（L-1…L-10）」。

**尺寸的硬规则（S-1…S-6）**（写进指南，作者与壳层都不必再商量。2026-10-07 改写：拖角手势撤掉后 S-2、S-5 作废，编号保留是为了不动各处引用；S-1/S-3/S-4/S-6 的口径不变，只是载体从手势换成了菜单与键盘）：

| #   | 规则                                                                                                                                                          | 为什么                                                                                                                                                                      |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| S-1 | **档位集＝`manifest.widget.sizes`，不引入任意 span**                                                                                                          | `packRight()` 的入参是 `size`、band 内排布硬编码「sm 两两配对 / md-lg 独占整行」（E16）；放开任意 span 等于把 packer 重写成占用网格模型，且 §4.4 R1「每档内容预算」当场失效 |
| S-2 | ~~拖角只改**跨列方向为主**，落点由 `spanPx(SIZE_SPAN[size])` 反查最近档~~ **（已作废 2026-10-07：没有连续换档手势，也就不需要「按像素宽度反查档位」这一步）** | 作废不等于白写：`nearestSize()` 已随之下线（`geometry.ts`），留下的口径是「换档只能是**从声明里挑一档**」——菜单与 `⌥←/⌥→` 都在 `sizes` 数组里取，永不产生中间态             |

| S-4 | 连续手势（拖拽摆放）期间给**吸附预览框**（ghost rect），松手才落库；离散换档**即时生效**，落库走 `setSize` 的防抖                                             | ghost 归宿主层画（偏差 28）；离散动作不需要「先预览再确认」，但写边界仍只在提交时，避免每帧 persist                                                                         |

| S-6 | 键盘等价物：卡片聚焦后 `⌥←`/`⌥→` 在前一/后一档间切换（**今天它是唯一的直接操作入口**）                                                                        | 手势不能是唯一路径（a11y；与 `⌘]`/`⌘[` 移序同族，见 §4.5 与 T4）；鼠标入口另有菜单档位组一处，两处写同一个 `instance.size`，权威只有一个                                    |

**拖拽摆放的十条硬规则（L-1…L-10）**：

| #    | 规则                                                                                                                                                                                                                                                              | 为什么                                                                                                                                                                                              |
| ---- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| L-1  | `pos` 的类型是**整数网格坐标** `{ col, row }`（列/行单位，不是 px）；跨度仍由 `size` 经 `SIZE_SPAN` 解出                                                                                                                                                          | 与 S-1 共用一个坐标空间：**离散换档与吸附式拖拽是同一套网格模型的两笔改动**，不新增第二套几何；像素 `pos` 会诱导「任意摆放」回潮                                                                    |
| L-2  | 落点吸附：拖动中把指针像素反解成 `{ col, row }`（`round((x-originX)/(CELL+GUTTER))`），ghost 画在**吸附后的整格位**上（由**宿主层**在桌面坐标里画——卡片带跟手 `transform` 且材质是 `overflow-hidden`，画在卡内会错位并被裁，见偏差 28）                           | 用户永远先看到「它会落在哪」，再松手；不存在半格状态                                                                                                                                                |
| L-3  | **落点必须整块空**（`w×h` 格全覆盖且不与任何已摆放件相交），否则**拒绝落点、回弹原位 + 一次短提示**                                                                                                                                                               | 不做「向下挤压」：挤压会让用户摆好的东西自己跑掉，比不让他摆更糟；拒绝是可预期的，重排不是。代价与替代见决策 11                                                                                     |
| L-4  | 净间距由网格天然保证：相邻格之间恒为 `GUTTER`                                                                                                                                                                                                                     | G-1 的拖拽侧等价物——吸附模型对了，间距就不需要额外规则；反之若允许像素摆放，间距得单独守，守不住                                                                                                    |
| L-5  | `pos=null` 永久保留为**自动流式**（新添加的件走 `packRight`）；**首次手动拖拽时把全部实例的当前自动位置固化成 `{col,row}`**（一次性迁移，无 IDB 版本变更，即台账 C-④）                                                                                            | 两种模式共存，缺省仍是「平台替你摆齐」；否则加了拖拽之后，「懒得摆」的用户反而得到更差的桌面                                                                                                        |
| L-6  | 键盘等价物：卡片聚焦后 `⌘⇧←/→/↑/↓` 按格挪动（越界与重叠同样拒绝并轻震式提示）；拖拽期间禁用 `transition`，落定才动（换档是离散即时生效，没有「手势进行中」这一段）；跟手位移**夹在摆放域内**（卡片不得越出网格，`placementBox()`，见偏差 28）                     | 手势不能是唯一路径（a11y，同 S-6/T4）；每帧跟手用 `transform`，避免 `left/top` 触发重排                                                                                                             |
| L-7  | 列序**从右缘往左数**（`col=0` 是最右列），行序自上而下；`rows/cols` 变小导致越界时，先按「整块仍放得下」向内收，**收完若与别的件相交、或本就收不下，则该件退回自动流式**（`pos=null`）并在溢出清单里给一句原因——不给「挤压邻居」留后门，与 L-3/决策 11 同一条口径 | 网格本来就是右锚定的（`widgetGrid()` 把右缘贴死、富余留左侧），列序若从左数，视口一变窄所有件会整体横移——右锚定列序让「贴右的仍贴右」。**越界必须有出口**，否则窗口一缩桌面就出现悬空地摆不回去的件 |
| L-8  | 换档（S 组）与挪动（L 组）**共用同一个占用判定**：目标格位集合必须全部为空，否则拒绝——换档放大到被占的格位时同样拒绝并回弹原档                                                                                                                                    | 两条路径写一套判定，才不会出现「换档能放大、拖拽不能挪过去」这种自相矛盾的桌面；判定入参就是 `{col,row,w,h}`，与 `packRight` 无耦合                                                                 |
| L-9  | **顺序与位置各管一段**：数组下标只决定**自动流式件**（`pos=null`）之间的排布序；一旦某实例有 `pos`，它脱离流式序列，`move()` / `⌘]` / 管理面「排序把手」对它**置灰并说明原因**（「已手动摆放」）                                                                  | 否则会出现两个权威打架：用户拖完位置又在管理面点上移，桌面没反应——这是 B6「看不见」的新形态。撤销手动态（清 `pos`）要作为一个显式动作给出来                                                         |
| L-10 | 拖拽只在**卡片空白/标题区**起手：起点落在件内可交互控件（勾选框、输入框、翻月箭头）上时不启动拖拽；拖拽期间 `setPointerCapture` + 抑制文本选中与 `contextmenu`                                                                                                    | 交互型件（待办、便签）最容易踩这条——否则「点勾选」会变成「把卡片拖走」，而这两种意图在同一个 24px 目标上无法区分。捕获与抑制是壳层的事，作者不该各自处理                                            |

**摆放域的左界（解 E18）**：推荐**标语让位**，不钳制列数——`Desktop.vue:43` 的大字标语在「桌面件占用 ≥2 个 band」时淡出（`opacity` + `duration-base`，一次性过渡，合 §4.11 动效口径），空桌面或单 band 时照常显示。三条理由：① 标语是**空桌面的装饰**，件一多它就该退场，这是语义而不是妥协；② 它的内容并没有丢——同一句 `brand.slogan` 常驻在顶栏（`TopBar.vue:36`），大字版只是它的装饰性重复，淡出不构成信息损失；③ 反过来钳 `cols` 要引入「壳层量一个文本块宽度再反推列上限」的跨层依赖，且**同一份 manifest 在不同语言/字号下能摆的件数会不一样**，这条不可接受。更狠的替代（直接删掉大字标语）见决策 12。**2026-10-06 补一条兜底**：`≥2 band` 只在宽带下等价于「压进标语区」——视口窄到只解得出一个 band 时，那唯一一条 band 的左缘本身就已越过标语右缘，band 数仍是 1。判据据此升为 `bandsUsed ≥ 2` **或**「与摆放域外接矩形相交」（外接矩形由 `WidgetLayer` 同源写进 `widgetRuntime.usedRect`，标语只量自己那一块的盒子），算术与反证见偏差 24。更狠的替代（直接删掉大字标语）见决策 12。

**明确不做**（同 §4.0 C-3 的口径，不因为加了 resize 和拖拽就松动）：`cols` 上限锁在 `BAND_COLS = 4`，`CELL/GUTTER/MARGIN` 与 band 模型不动，因此**没有**「特大件」「跨 band 拉宽」这类形态；要更宽的表达力走「同一 kind 声明更多档（含 `4×3` 这类中间档）」——那是**声明**问题而不是几何问题，仍然受 R1 每档要有内容预算的约束（宁缺不夹生同样适用于新增档）。准确说，新增一档＝给 `SIZE_SPAN` 加一个 `{w,h}` 条目并同步 §4.4 的容量表与 R4 的行数上限，`CELL/GUTTER/MARGIN/BAND_COLS` 与 `packRight()` 都不动——**它仍是离散档，不是任意 span**（决策 9 的另一条路指的就是这个）。

**顺带把 E7 的一处「预留」结清**：吸附落点仍是离散 `size`，所以 `WidgetFrame` 上那个 `cq-widget` 容器根**继续不需要定义变体**。按决策 9（不放开任意 span），它永远等不到「连续缩放」这个用武之地——留着它唯一的价值，是在指南里替作者把「件按档渲染，不按像素渲染」这句话钉住。本方案选「不删也不启用」，并在 §8 把这句口径回写进《开发指南》附录，避免下一个人以为 resize 需要它。

**桌面速览**（补 E10）：顶栏加一个「显示桌面」按钮 + 快捷键，语义为「窗口层整体下移/透明化，再点还原」，与 Dock 已有的窗口级联动作同族。它服务整个小组件层（桌面当前没有图标层，`Desktop.vue` 只有壁纸与标语），成本是一个 `shellUi` 布尔 + 一个过渡类，比「把小组件提到窗口之上」干净（后者会破坏 D10 的层语义）。

**呈现层口径（2026-10-07 体验重构定，实现见 `WidgetConsole.vue` 一族）**：

- **对比即结构**：「你拥有的＝台账，你可挑的＝陈列墙」——桌面段是等高紧凑的台账行（行高 ≈138px，预览不再按真实档位撑高整行），目录段是预览主导的陈列卡墙（`cq-window` 响应式：窄 1 列 / 中 2 列 / 宽 3 列，断点沿用 §3.4 的 480 / 800）。管理面的两个任务（管记录 / 挑组件）各得其所，这就是 B5 诊断的呈现层落点。
- **取景两式、比例尺一把**：台账行与陈列卡共用**统一比例尺**（锚在 lg 档宽 344，同段所有预览同缩放比）——台账是同一张纸上的账，必须保住「桌面上多大」的相对真值，且换档变形肉眼可见（「尺寸所见即所得」的前提）。差别只在取景框：台账定框 96×96 居中留白（行高因此恒定），陈列卡铺满卡宽、高度随件自然长（选「大」卡就真的变大）。**曾试过 contain 尽览（各自放大到框满），实测被否**：sm 与 lg 在同一个框里等大，尺寸差异和换档变形一起消失，正是这张界面最不该丢的信息。缩放的是真实渲染卡片（§4.8 预览条目不变），不是截图资产。
- **签名元素：网格尺寸字形**——4×4 点阵里点亮 `SIZE_SPAN` 的真实跨幅（sm 2×2 / md 4×2 / lg 4×4），出现在台账行当前档（分段控件段内）、陈列卡支持档位行、尺寸选择条选项。形状承载语义（不靠颜色，守 §4.6），它就是 D15「整数网格 + 离散档」模型的可见化；缺省 `aria-hidden`（纯形状、无文本节点，不污染 radio 标签与 `hasText` 过滤）。
- **状态显式分级**：未显示＋成因 / 已禁用 / 已手动摆放 用 Badge 语义色三级表达（未显示取 warning），不再用灰字一档糊过去。
- **「预览」角标降权但 A-13 约束不变**：角标从实心深色 chip 降为 micro 级安静字形（eye 图标 + 文案，ink-mute 无底色）——它标注的是「这是假的、不可点」，不该是全行最响的元素；「必须标『预览』且不可交互」（A-13）原文照旧，降的只是音量。

- **换尺寸有两个入口，但权威只有一个**：桌面卡片菜单的档位组（§4.7 第 2 步）与管理面实例行的分段控件（离散、键盘可达、溢出清单里「换小一档」也用它）写的都是同一个 `instance.size`。这不违反本节「消除重复表达」——那条打的是**同一段视图里出现两个语义不同的同名控件**（E8 的病），不是打「同一件事有两个入口」。**去重补一条（2026-10-07）**：实例行的分段控件**就是当前档的唯一表达**（选中段内带尺寸字形），行首那个单独的档位文字删除；单档 kind 没有分段控件时，才在行首给一枚「字形 + 档位标签」chip。同一状态在同一行只说一遍。
- 尺寸选择**移到「添加」的弹层里**（点添加 → 选档 → 上桌面），这样「尺寸」在目录区只出现一次、且发生在它真正有意义的时刻。(HIG) 把这条从「我们觉得重复」升级为明确规范：「将小组件的各种尺寸分组在一起，并提供单一描述……以免用户误认为每种尺寸是一个不同的小组件」（A-4）。
- **一行描述**的写法照 (HIG) H-5 执行：以**操作动词**开头（「查看某地当前的天气状况和预报」「跟踪临近日程和会议」是我们的模板），**禁止自指**（「此小组件显示…」「使用此小组件来…」「添加此小组件」），句子式大写。这条可静态扫描（T9），因为 `descriptionKey` 一旦进语言包就会漂。
- **预览用真实渲染**：把 `manifest.entry` 挂进一个 `pointer-events:none` 的固定尺寸容器，喂 schema 默认配置 + 一份内置样例数据。不用截图资产（会漂）。(HIG) 的对应口径是「设计逼真预览以显示在小组件库中…如果数据需要太长时间生成或加载，应转而显示逼真的模拟数据」（A-5）。副作用是好事：**件必须能在「无真实实例上下文」下渲染**，等于给 `useWidgetContext` 加了第二个消费方，反过来验证契约干净。
  - 代价与约束：预览沙箱只渲染进入视口的行（IntersectionObserver 懒挂载），一次并发 ≤ 4；沙箱容器 `aria-hidden`（不进读屏顺序，避免与列表文字重复播报）。
  - **沙箱的三个屏蔽**（不是打磨，是 C-① 的护栏——少了它们，「真实渲染预览」就把副作用漏到了用户数据上）：① **数据**——`useWidgetData` 在沙箱内返回件自带的样例文件（约定 `src/widgets/<id>/preview.json`，键与 `manifest.data` 对齐），**不读真实 VFS**（样例里的自然语言文案不得写死在 `preview.json`，要走 `widgets.preview.*` 进 §4.11 的齐平门禁，否则英文界面的预览会显示中文）；② **写**——`write`/`patch` 为 no-op 且在 dev 下抛断言，预览永远改不到用户的东西；③ **调度**——`useWidgetTick` 不注册进宿主调度器（预览是静态一帧），否则一屏十几行目录会挂出十几个秒级定时器，正是 E11 的反面。
  - **必须标「预览」且不可交互**（(HIG) A-13：「避免在 App 内镜像小组件的外观。在 App 中包括外观与小组件类似但行为却不相同的元素可能会造成用户困惑」）。这条是本方案唯一**主动制造**该风险的地方，所以约束不是可选的打磨，是采纳前提；同理，**应用内不得复用件卡片样式**（§4.9 的件与应用是两个 UI，不是同一套皮肤）。
- **搜索框**消费 `keywords` + name + description——把 E7 的「预留」落地；**两段同步**（2026-10-07）：搜「时钟」时「桌面上的小组件」与「小组件」货架一起收窄，不出现「上面纹丝不动、下面只剩一件」的割裂感；两段各给空态，桌面段空态带「去挑一个」行动（滚到货架），空态是行动邀请不是终点。
- **目录行对当前会话无权限的 kind 给灰态 + 「需要 <角色>」**（(HIG) H-10：「当认证有价值时，告诉用户这一点」）。现状是 `canAccess` 不满足就从货架消失，用户既不知道少了什么、也不知道去哪儿拿；灰态行只做**告知**，桌面渲染口径不变（仍然不摆鬼件）。
- **「添加」按钮消费 `tint`**（(HIG) H-12）：磁贴渐变之外，目录行的添加按钮/焦点高亮用同一档 tint——`tint` 从纯装饰变成语义色，也让「未安装/已安装/无权限」三态在色彩上有单一来源。
- 抽屉与中心仍是「一份实现、两个外壳」：抽屉给「目录 + 当前实例紧凑行」（快改），中心给完整台账 + 数据段。**数据段折成一行**（2026-10-07）：OsCollapse 收起，头条带孤儿计数徽标，有孤儿数据时自动展开——它一月用不上一次，不该常驻占版面。面板实现仍是 `WidgetConsole.vue` 单点，两宿主共用；根节点自带 `cq-window`（抽屉宿主没有容器查询祖先），断点语义与窗口宿主一致。

### 4.11 横切约束

- **i18n**：新增 `widgets.descriptions.*`、`widgets.configOptions.*`；现有「两份语言包叶子 key 齐平」门禁自动覆盖；把「同语言内取值互不相同」从 `apps.*` 扩到 `widgets.names.*`（内置件一多，撞名概率立刻上来）。**`descriptions.*` 的写法进门禁**（T9，(HIG) H-5）：中文不得以「此小组件/本组件/使用本」开头，英文须句子式大写。
- **a11y**：卡片可聚焦 + §4.5 键盘路径；预览沙箱 `aria-hidden`；每秒变化的时间文本**不得**进 `aria-live`（现状如此，保持）；「⋯」菜单项要有可访问名，不能只有图标；配置面四类字段控件同理要以字段标签作可访问名——开关本体尤其容易漏：它的按钮内容只有一个无文字的旋钮，而渲染器把字段标签画成它的兄弟节点，两者之间没有任何可访问名关系，只能显式传 `aria-label`。新增两条地板：件内**文字 ≥11px**（(HIG) H-2）、**命中区 ≥24×24**（(HIG) H-4）；对比度之外再加「去色仍读得懂」（(HIG) H-3，目视基线，见 T10）。
- **动效**：只允许**数据更新的一次性过渡**（进场/数值变化），时长消费 `duration-quick`/`duration-base`，且 (HIG) A-11 给的上限是两秒——我们的 `duration-base` 远小于它，因此取更严：**件内禁用持续动效**（呼吸、循环 shimmer、轮播），也禁超过 2s 的过渡。骨架的 `animate-pulse` 属加载态例外，且预览沙箱不渲染它。
- **性能**：共享调度器（E11）；预览沙箱懒挂载 + 并发 ≤ 4；`check-bundle` 复看——10 件都是异步 chunk，但 `WidgetConsole`（含预览与菜单）会明显变大，需要拆出预览子块。

### 4.12 配置面：schema 打底 + 件可覆盖（解 B4 的配置半边）

「每个小组件有自己独立的配置界面」这句需求，落到本项目的现有机制上要**先纠一个口径**：不是「每个件都必须有自己的面板」，而是「**每个件都可以有**」——缺省态仍由宿主按 schema 统一渲染，件声明 `configEntry` 才换成自绘。因为指南 §6 那条「控件由宿主渲染，小组件不写表单」不是偷懒，它同时守着三样东西：管理面可读（§4.8 的预览沙箱要喂 schema 默认值）、写边界可收敛（`sanitizeConfig` 按 schema 丢未声明键）、i18n 齐平门禁可扫（`widgets.config.*`）。全量反转的代价大于收益。

**三层归属，一刀都不含糊**：

| 归谁             | 负责什么                                                                                                                            |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| 件（内容层）     | 配置的**表达**：控件形态、分组、字段联动、需要搜索/实时预览的选项集                                                                 |
| 宿主（平台层）   | 配置的**通道与容器**：面板外壳（抽屉内联 / 小组件中心 / 卡片菜单「配置…」弹层三处同一实现）、草稿与提交、脏值提示、材质、焦点与 Esc |
| schema（契约层） | 配置的**真相**：键集、类型、默认值、边界、i18n key——**声明 `configEntry` 也不能不写 schema**                                        |

**契约**：`WidgetManifest` 加可选 `configEntry?: () => Promise<Component>`。面板组件同样 prop-less，走新 composable `useWidgetConfigPanel()` 取上下文：

```
{ instanceId, schema, values /* 草稿 */, patch(partial), commit(), reset(), close(), status }
```

规则（作为指南 §6 的替换文本）：

1. **`patch` 只改草稿，`commit` 才落库**——`updateConfig → persist` 走 §4.2 的 300ms 防抖与 `snapshot()` 剥代理。这直接堵住 E6 的「每个击键一次 IDB 写」，也避免自绘面板各写各的。
2. **写边界不变**：`commit` 的内容仍过 `sanitizeConfig`——件在面板里塞进 schema 之外的键会被**静默丢弃而不是报错**。自绘画布因此拿不到越权写的能力，这是台账 C-⑤ 的主护栏。
3. **面板不得出现平台动作**：不能放「移除件 / 换尺寸档 / 停用 / 打开关联应用」——那些归卡片菜单与管理面（§4.8）。面板只做配置，否则配置面变成第二个管理面，内聚立刻散掉。
4. **不得自绘材质**：面板容器由宿主给（复用 `src/ui` 弹层族，与 `ContextMenu` 同族），面板内只允许 `src/ui` 控件 + token 派生类。这与 §7「不把桌面卡片材质搬进 `src/ui`」正好对称：**桌面件材质与管理面材质是两套**。
5. **必须能在 mock context 下渲染**：§4.8 的预览沙箱与 T6 同构断言一并覆盖 `configEntry`——否则「打开配置就炸」只有用户能发现。
6. **文案进语言包**：面板自造文案走 `widgets.config.*`，受齐平与去重门禁（§4.11、T7）。

**什么时候该声明 `configEntry`**（判据，别凭手感）：schema 四类控件表达不了才算，具体是四类形态——① 选项集需要搜索或远大于 6 项（时钟的第二时区选城市）；② 字段间有联动（选了 A 才显示 B）；③ 需要分组小标题与说明段；④ 需要实时预览（壁纸/强调色选择器）。**单个开关、单个数字、单个下拉一律不值得写面板**——用 schema，白拿管理面统一渲染与 i18n 门禁。

**与 (HIG) H-9 的关系要说清**：`≤3 项` 管的是 **schema 的项数**，不是控件形态。自绘面板**不是**绕过项数上限的后门——评审数的是 schema 有几条，不是面板画了几排。这条不写死，「独立配置界面」就会退化成「把八项设置重新塞回件里」的正当理由。

**验收 T12**（新增，三条都可机器判）：静态扫描 `configEntry` 指向的组件——① 不得 `import` `@/kernel/stores/*`（只准 inject）；② 不得出现 `setSize`/`remove`/`uninstall`/`setEnabled` 调用或等价命令串；③ 有 `configEntry` 的 kind 必须同时有非空 `config` schema。

## 7. 明确不做

真天气 / 新闻 / 股票等需要外部数据源的能力（纯前端约束，且与「不建 mock server」的既定口径冲突）；小组件堆叠与智能堆叠；锁屏 / 通知中心形态的件；实时活动（Live Activity）；跨设备同步；件内滚动（R3）；件与件直接 import 通信（继续只走 CommandBus / VFS）；把小组件卡片材质搬进 `src/ui`（`WidgetFrame` 单点不变）；撤销（undo）——等通知中心支持 action 按钮再谈。

**按 HIG 对照后新增的「不做」**（§4.0 C 组，逐条都有出处，不是懒）：

- **补充小组件四形**（圆形/圆角矩形/内联/矩形）：它们是锁屏与表盘的载体，本项目没有对应宿主（C-1）。
- **色调（accented）外观与「用户给单个件选色」**、**虚化（vibrant）全量渲染模式**：它们解决「系统把件搬到别的材质上」的多环境问题；我们只有桌面一处、材质自己控，只采纳其两条推论（不透明灰度前景、颜色不承载唯一语义）（C-2）。
- **特大档**：需要把 band 从 4 列扩到 8 列＝重做几何；且 HIG 自己说「创建一个最合适的档」优先于「提供所有档」（C-3）。
- **件内 Dynamic Type（rem 化以支持系统字号放大）**：桌面 Web 的等价物是浏览器缩放，px 令牌已随页面等比缩放；rem 化会与 `--text-*` 令牌层冲突（C-4）。
- **全天候显示/待机显示/CarPlay、visionOS 安置与处理样式、watchOS 智能叠放相关性**：无对应平台（C-5）。
- **WidgetKit 式时间线/后台刷新预算**：Web 无这一层，改由「共享调度器 + `visibilitychange` 暂停」达到同一目的（C-6）。
- **纯入口件**（一键拉起应用的图标网格）：内容＝Dock 已有图标的子集，按 HIG 判为无额外价值（H-6/E15）。
- **任意像素级的自由缩放 / 自由摆放 / 跨 band 拉宽**：换档是**离散**的（菜单档位组与 `⌥←/⌥→`，都只在 `manifest.widget.sizes` 里挑，S-1/S-6）；摆放是「连续手势 + 离散吸附」——吸附到格（L-1/L-2）。放开像素级自由缩放要把 `packRight()` 重写成占用网格模型并放弃逐档内容预算（R1），代价与收益都不成立（决策 9）。
- **配置面板里的平台动作**：换档、移除、停用、卸载一律不在配置面板出现（§4.12 规则 3）；面板只做配置，别把它养成第二个管理面。

### 实现偏差（回写时逐条对代码实测后落账，2026-10-07）

1. **`interactive?: boolean` 成为显式契约字段**（本文 §4.5 原文靠「有没有可交互控件」推断归类）。实现里三类件（展示/交互/入口）的区分落到了 manifest 的一个显式布尔上，`WidgetFrame` 的拖拽起手排除（L-10 的 `[data-widget-interactive]` 选择器）与考卷归类都以它为准。理由：靠推断归类会让「同一件在不同宿主行为不一致」变成隐性状态——字段成本一个布尔，换来确定性。
2. **待办 md 档比 R4 预算更保守**：md 渲染 3 行 + 「还有 N 项」收口（lg 按 `config.limit` 3–8 行 + 底部就地添加）。R4 给 md 的行预算是 4，实现取 3——因为 md 内容区实测约 322×138px（`--spacing-widget-compact` 边距下），4 行 + 表头会把行高压出 R4「不许缩字号塞内容」的红线；「还有 N 项」本身就是下钻的预告，符合 H-1。
3. **控制中心 md/lg 的交互目标数按 R4 的字面数值超标——2026-10-06 评审已结案，改的是判据单位不是这件件**（原判「标为待评审、不算达标」）：按「每行一组开关」排布，md 一行一组、lg 五行。评审先问的是「R4 那个数字到底在数什么」，本文原先没定义，于是同一件在不同读法下分别是 4/11/12 个目标——一个没有单位的数字没法评。定口径（写进 §4.4 R4）：**目标＝决定**，互斥选项一排算一个；「一行一个独立决定」的列表型正文按**行数上限**封，不按个数封。按此：`control-center` md＝4 个决定＝该档行上限 4（内框实测 310×126、used **100%**）、lg＝5 个决定 ≤ 行上限 8；每个 chip `h-6 min-w-6`＝24×24（T4 在册读数为最小 24×24）；下钻必答走「设置 › 外观」（`DRILL` 腿在册）。于是这条结案为**达标**，不是豁免——它同时留下了反证：**「把 md 砍到 2 组以满足字面 2 个」这条路会把这件判红在另一条腿上**。md 内框 126px 里两组 chip 只有 48px 内容（包围盒 38%），连续死白带 ~50% 撞上 §9 T2 的 15%，而 T2 是自动化门禁、R4 的数值判据按本文 §4.4 明写「不进自动化，改为 §4.9 逐条人工核对」——两条打架时以有机器腿的那条为准。若真要保字面数值，唯一自洽的走法是撤掉 md 档（R2 宁缺不夹生），而 md 是它的 `defaultSize`、撤档等于撤回批次 B 已交付的 §4.9 考卷，这条不在本线范围内。批次 B 交付时的原始分歧记录已随该批临时文件退役，结论以本条为准。
4. **日期敏感的预览样例由代码生成，不走静态 `preview.json`**：待办/月历的样例来自 `taskSchedule.ts` 的 `sampleTasks()`/`sampleEvents()`（锚定「今天」），其余七件的样例在各自 `preview.json` 里、文案走 `widgets.sample.*` i18n key，仅在 `preview === true` 时解析。理由：静态日期会被「今天」筛选条件滤空，预览会成一张空卡（§4.8 屏蔽 ① 的数据源注释即此）。
5. **预览沙箱用 mock WidgetContext，不塞假实例**：容器侧 `createWidgetContext()`（真实实例）与 `createPreviewWidgetContext()`（不进实例表、配置取 schema 默认、`setSelected` 空操作）产出同一形状的上下文，经**单一注入键** `WIDGET_CONTEXT_KEY` provide；件内只有 `useWidgetContext()` 一个入口。本文 §4.8 原文写「容器 provide 一份上下文」，实现把「沙箱绝不污染 `widgets-v1`」钉成了构造函数层面的分离。
6. **卡片菜单「配置…」开的是宿主弹层，不是 `OsDialog`**：`WidgetLayer.vue` 内 `role="dialog"` 的自绘弹层（Esc/点遮罩关闭），因为 `OsDialog` 的「取消/确认」一排与配置面板页脚的「恢复默认/完成」是同一件事的两份表达。本文 §4.12「面板容器归宿主、三处共用」成立——`WidgetConfigPanel.vue` 的两类宿主是弹层与实例行就地展开（抽屉与中心经 `WidgetConsole` 共用后者）；偏差在于「三处」实际是「两组件、三入口」。
7. **文件类件的下钻 payload 带 `{ path, key }` 两个字段**（storage/recent-files → file-manager）：windowManager 的多实例复用（架构 D4）只在 `payload.key` 匹配时发生，只带 `path` 会让「点开不同文件却复用同一扇窗」。`path` 给内容、`key` 给窗口身份，缺一不可。
8. **标语让位的判据是 `useWidgetRuntime().bandsUsed`**：由 `WidgetLayer` 把 `placeWidgets()` 的落位结果折算成「占用了几个 band」写入运行态 store，`Desktop.vue` 只读这个数（≥2 淡出大字标语）。本文 E18 原文说「件多于一个 band 时」，没定谁持有这个判定——实现把它放在摆放求解的现场（几何权威所在），而不是让 Desktop 反向解析网格。
9. **§4.3 自动刷新的接线形态**：`WidgetLayer` 按每个实例 `manifest.refresh` 的 `REFRESH_PERIOD` 经共享调度器（`subscribeTick`，同周期合并计时器）触发 `widgetRuntime.requestRefresh(instanceId)`，件内 `useWidgetStatus.onRefresh` 消费；`day` 档的周期值（60s）只是**检查间隔**，真触发看日期串变化；`visibilitychange` 隐藏即 `setSuspended()`，回前台补扫一次。本文只写了「live/minute/hour/day/manual 四档语义」，没写这条「宿主统一驱动、件只应答」的管道；`live` 的周期实现为 60s（对应「秒级件靠 requestAnimationFrame 自转，宿主刷新只做数据重读」的口径）。
10. **配置面通道分「造对象」与「注入」两步，漏注入不报错**（本文 §4.12 只写「宿主给容器与草稿/提交通道」，没定这条护栏落在哪一层）：`createWidgetConfigPanel()` 只产出 api，必须再经 `provideWidgetConfigPanel()` 才写入 `WIDGET_CONFIG_PANEL_KEY`（`src/kernel/composables/useWidgetConfigPanel.ts:102`），件侧拿不到通道时静默渲染空面板。这个分离真实失效过一次：漏掉 `provide()` 让 `configEntry` 的三处宿主（卡片菜单弹层 / 管理台实例行 / 小组件中心）全灭——抽屉空白、中心点进去炸，而 `vue-tsc` 与其余门禁全绿。故 `tests/unit/widget-config-panel.test.ts` 把「宿主必须注入」钉成一条去掉 `provide()` 必红的守卫。

16. **§4.2 的「300ms 防抖合并」合并的是同一路径，不是同一 handle**：本文只写了「300ms 防抖合并」，没定这份挂起值挂在谁身上。实现第一版把它挂在每个 `useWidgetData` handle 自己身上，于是撞出两类丢更新——① 同一 handle 在窗口内连写两次，第二次以「读得到的旧底」（此刻 VFS 还没 flush）为基，把第一次整条吃掉；② 同一份 `shared` 数据本就允许多个写者（`todos` 的 md/lg 两张卡各一个 handle，「今日」应用直接写同一个 `tasks.json`），各存一份 pending 时跨写者互相覆盖。用户可见症状：快速录两条待办，reload 后只剩最后一条。修法是把挂起账提到**按 VFS 路径共享**，并且它不属于任何一个调用方——账本放在寻址权威所在处的 `src/kernel/widget/widgetData.ts`（`hold`/`release`/`peek`/`readWidgetDataJson`），件侧 flush 与「今日」应用的同步读改写走同一条读写边：应用读要读到卡片窗口里那一条，写完 VFS 就把那份挂账作废，否则卡片下一次 flush 会把应用这条倒回旧底。这条不是「给某个件打补丁」：它把 §4.2 的乐观读语义定成了「路径级单一真相」，多写者天然互相看见。判据三条腿——单位级 `tests/unit/widget-data-debounce.test.ts`（同 handle 连写、跨 handle 连写、persist 失败回滚、件外写者与件内防抖写共存），动线级 `tests/e2e/widget-persistence.spec.ts` 的「300ms 内连按两次 Enter → 两条都在 → reload 后仍是两条」（它先是作为 `test.fixme` 记录实测失点写进来的，修好后转正）。两条单位级判据各自做过反证：把读边退回「只读 VFS」、或把应用那次写完不作废挂账，用例分别红。

17. **(HIG) A-9 的「更新于」按档位分别落位，不是一张统一的底部行**（本文 §4.3 只写「件内可显示」，没定它落在哪一层；实现期量出来的算术逼出了三种形态）：md/lg 的内框 126px 在 R1 预算下已被内容排满——实测 `system·md` used **100%**、`notification-summary·md` **97.6%**、`data-summary·md` **97.6%**、`todos·md` 96.3%（`widget-acceptance.spec.ts` 的 deadTable 读数），再多一行流式内容就被卡片的 `overflow-hidden` 静默裁掉（新加的越框腿实测过：塞一个 64px 的占位块进 `data-summary·md`，立即越出 **bottom 35px** 并判红）。于是四件各自的落法是：`storage`（sm/md）走**列表尾行**（该档本就有余量，sm used 14.3%）；`system·md` 走**第 6 格**——它本来就是 2×3 的网格且已占满 3 行，补一个同尺寸的格子不加高度，`system·sm` 才走底部行；`notification-summary`/`data-summary` 的 md 走**标题行右端**（不加行就不越框）。适用面同时收窄并逐件给了理由（机器腿 `A9_KINDS`）：只有**数据源独立于观看者**的四件有读数（storage/system 读浏览器 API、notification 读别的写入、data-summary 读外部 fixture）；`clock` 内容即时间、`calendar`/`todos`/`sticky-note`/`control-center` 的变化就是用户自己的动作（永远最新，`refresh: 'manual'` 或即时生效）、`recent-files` 每条自带行级相对时间（卡片级汇总会把同一信息说两遍）。相对时间口径统一见 §4.3。
18. **T2 补了反方向的那条腿：内容越框＝裁切，判红**（本文 §9 T2 只写「连续死白 ≤15%」，即「太空」这一侧）：卡片是 `overflow-hidden`（§4.6 材质），内容超出内框时不报错、不留滚动条，直接被裁——而「挤出去」在旧口径下是**看不见**的，死白读数反而更好看。A-9 那批改动要占行高，正是最容易把某档推出内框的动作，所以先补这条腿再动预算（`CardReading.spill` 四向像素之和判 0，十件 × 全档当前全绿）。顺带把 `used`（内容包围盒/内框）也摊进 deadTable，作为「这一档还剩多少」的唯一权威读数——上面那条落位裁决就是拿它判的。
19. **播种的读回必须放在 reload 之后复核**（本文未列，属测试基建的确定性）：`widget-acceptance.spec.ts` 的 `mount()` 原本在 reload **之前**poll 到「库里就是我们播种的那份」即放行，但冷启的 `seedDefaults()` 与 `useWidgetData` 补默认值都是 fire-and-forget 的**整树刷盘**，可以落在这次读回之后把 `fs-v1` 盖回去——于是 reload 起来的是空数据的桌面：卡片照常渲染、档位照常对，件内却没有列表项，表现为一句 30s 的定位超时（两 worker 并发跑 `widget.spec.ts` + `widget-acceptance` 时偶发，单跑必绿；`T1 todos·lg 勾选完成` 是撞上的那一条）。改成「播种 → reload → 复核库 → 不匹配就重播一次再 reload」：第二次 boot 时文件已在库里，补默认值那条路不再触发。同一条根因适用于所有直接写 IDB 的桌面用例。

20. **月历 lg 的 24×24 地板会被「6 行的月份 + 议程满」挤掉，让位的是议程行数**（本文 §4.4 R4 与 §4.9 的月历考卷都只算了默认那一屏；旧 T4 一直绿，是因为它量的是种子给的那个月，而 6 行的月份每 2~3 个月就来一个）：日格行高走 `minmax(0,1fr)`——件内注释的原话是「月视图有 4/5/6 行三种形态，写死必溢出」，所以它**不是设计值，是余量**。lg 内框 320px（344 − 2 边框 − 22 `compact` 内衬）里标题行 29 + 星期表头 18 + 根间隙 12 是固定的，议程块按当天事件数吃高：3 条（无计数出口）93px、4 条起 115px。于是 6 行月 + 满议程时网格只剩 `320 −（29+18+12+115）= 146px`，减掉 5 条行间距 20px ⇒ 每格 **21px**，实测读数 `查看 30 日 → 42.3×21`，正面撞上偏差 14 刚立下的「地板就是地板」。修法按 R3 走：**议程给网格让一行**（`agendaMax = rowCount ≥ 6 ? 2 : 3`，多出来的落到那行「还有 N 项」），实测回到网格 168px、每格 **24.7px**、议程 93px、四向越框 0。没有把 `minmax` 改成写死 24px：那样 6 行月 + 满议程会让网格整体顶出内框，被卡片的 `overflow-hidden` 静默裁掉——正是偏差 18 那条腿要罚的形态。让位的为什么是议程而不是日格：日格是 lg 这一档的**主结论**（§4.9 考卷「月网格 + 当日日程」，前一半），议程是附注，且它自带合规的退场方式（计数出口）。
    同一轮把播种的数据量抬到**撞得到上界**：`events.json` 4 条（少一条就没有「还有 N 项」那 22px，最差形态不成立）、`tasks.json` 9 条（`limit` 的 schema `max` 是 8，只给 4 条时「8 行清单排进内框还剩多少」这条算术永远量不到），并补第二条最差配置腿 `T4 todos·lg 配满行预算（limit=8，正文 9 条）`——实测标题行 + 8 行 + 计数出口 + 就地新增四段排在 320px 内（越框 0）、命中区最小值仍 24×24，这一档此前无腿。**判据读数以 2026-10-06 复测为准**（播种条数变了）：`calendar·lg` used 98.8%、`todos·lg` 98.8%、`todos·md` 96.3%（不变，md 恒 3 行 + 出口）、`control-center·md/lg` 100%、`recent-files·lg` 82.3%，其余与偏差 17 那批同值。附带一条测试纪律：T1 的三条 todos 用例的期望数组改为从 `SEEDED_TASK_TITLES` 这一个源头推——手抄的那份在种子一变的当刻红了 4 条，这是本轮实测到的，不是预防性说教。同一根因的**排查面已全仓扫过**（2026-10-06）：塌陷要两个条件同时成立——① 可交互目标的**高度由剩余空间倒推**，② 那一屏的内容体积由**数据或配置**决定。`grep minmax(0` 在 `src/widgets/` 只命中月历的 `bodyGrid`（条件 ①）；纵向 `flex-1` 的容器另有四处（待办与通知摘要的 `<ul>`、便签 textarea、数据摘要指标块），但它们的可交互子项都是固定高度（`justify-start` 的 `<li>` 里挂 `h-6 w-6 shrink-0`、通知摘要的行是纯 `<li>` 文本而命中区是那颗 `h-6 shrink-0` 标题行、数据摘要那块是非交互文字），容器被拉满只产生空白、不压缩命中区。所以只有月历需要最差形态腿，不给十件铺同一条。

21. **「断言什么都没写」的判据不能用两次相邻读数相等来定**（本文 T1 反向腿的原写法，2026-10-06 由审计回扫发现并修）：`useWidgetData` 的落库有 `DATA_WRITE_DEBOUNCE = 300ms` 合并窗口，件内 `write/patch` 之后立刻读 IDB，看到的是「还没冲出去」的旧值；同一份旧值过 50ms 再读一次仍然相等，两条相等读数就把「尚未落盘」与「永不落盘」判成同一种东西——**这是自绿，不是通过**。修法是在断言前立一根**静默地板**：`quietFloorAt = Date.now() + 2 × 300`，用 `expect.poll` 轮询快照，只有「与上一次读数相同 _且_ 已过地板」才返回 true，随后再做内容比对。同时把比对单位从「路径名集合」换成**整份快照**（`JSON.stringify(kv['fs-v1'])`，路径名 + 每个节点的内容都算进去）：只比名字时「改写了 `events.json` 但没增删文件」这一形照样绿，而它正是这条腿要防的写盘。反证实测：往月历的「翻月」动作里注入一句 `file.write({ events: [] })`，旧判据**绿**，新判据报 `Error: fs-v1 动了`。另有一条同形状的守卫：腿里那两个动作（点日期、翻月）各自要断言「这一动真的动了」（`aria-pressed=true`、月标题文本变了），否则两个动作里有一个是空跑，反向断言就在测一张没被碰过的屏。这条口径适用于本线所有「不写盘」判据，不只 T1。
22. **一个契约有多处守卫时，反证要挑「会被告知的观测点」下手，不是把每个守卫都碰一遍**（2026-10-06，T8 预览懒挂载）：懒挂载链上有三处看起来都是「门」——`WidgetPreview` 里 `syncSlot` 的 `inView.value &&` 前置、`previewBudget.schedule()` 里的 `waiters.findIndex((w) => w.inView())`、模板的 `v-if="live && kind"`。把前两处分别改成恒真，**全量一条都不红**：`syncSlot` 只在 inView 发生跃迁时被调用，那个 `&&` 在测试里根本走不到被证伪的分支；预算的 `findIndex` 在「所有行都视口内」的场景下与不带过滤的写法等价。唯一能让这条契约失效的 mutation 是**让观察者说谎**（`stubInView` 的初始态与广播值可控），所以反证只这一支有信息量。由此定下一条排查纪律：**mutate 前先问「这个守卫在测试的调用序列里有没有被真正求值」**——守卫多不等于有腿，而连续两三个 mutation 全不红通常意味着缺的是**一整条腿**（这里缺的是「视口外一槽都不申请、一棵都不挂」那条三态腿：视口外 → 进视口 → 滑出还槽，`previewSlotState()` 读数 `{0,0} → {3,0} → {0,0}` 加 DOM marker 数 `{0,3,0}`），不是守卫写错了。与偏差 20 的「config 门控逐个 mutate」是同一条纪律的两个方向：那说的是「有腿的判据要各自证伪」，这说的是「自绿的 mutation 不能当成契约已被保护」。

23. **卡片卸载钩子不得清理仍属于实例的平台状态；静态播种的腿测不到动态跃迁**（2026-10-06，§4.10 溢出治理）：`WidgetFrame.vue` 曾挂 `onScopeDispose(() => runtime.forget(props.instanceId))`，本意是「卡片没了就收掉它的运行态」。但**卡片离开 DOM 有两种成因**：实例被移除（该清），以及视口变窄把它挤出摆放域（不该清——那一条溢出记录正是「+N 个未显示」清单的数据源）。窄窗那一刻的时序是 `WidgetLayer` 的 watcher 先写 `{visible:false, overflow:'no-space'}`，随后卡片随 `v-for` 卸载、`forget` 把刚写的这条删掉 ⇒ chip 计数归零、件**静默消失**，用户看到的是「我的小组件不见了」，§4.10 的出口恰恰在最需要它的动线上失效。修法：`forget` 随**实例**生命周期走（`widgets.remove()` 与 `uninstall()` 各清一次），`WidgetFrame` 不再碰运行态。为什么 T1~T15 加溢出治理那四条腿全没抓到：那四条一律用 IndexedDB **静态播种**五件 lg 到 900×620——进壳层那一刻就放不下，卡片从未上过桌面也就从未卸载，`onScopeDispose` 一次都没跑；缺的是**跃迁**那条腿。新增 `widget-overflow.spec.ts`「动态溢出」：三件 md @1280×800 全放下 → 700×700 挤出一件 → 清单行给「今日待办 / 中 / 桌面已放满」→ 回宽自己回来且不留幽灵溢出。反证实测：把那行 `onScopeDispose` 装回去，`1 failed / 4 passed`——**只有这一条红**。口径适用于所有 `onScopeDispose`/`onUnmounted` 里的 store 清理：**先问这条状态在该卸载成因下还算不算数**；凡「A 状态由 B 位置写出、又被 C 生命周期清掉」的清理，判据要覆盖**跃迁**（宽→窄→宽）而不只是终态播种。

24. **标语让位的判据在窄窗口会漏：`bandsUsed ≥ 2` 之外要补一条真实矩形相交**（本文 E18 / 偏差 8）：偏差 8 把判定放在摆放现场、`Desktop` 只读 `bandsUsed`，这在宽带上等价于「件压进标语上方」——网格右锚定，是第二个 band 才横切进左侧标语区的。但视口窄到只剩一个 band（`cols < 8`，约 <700px）时，唯一那条 band 的左缘 `originX + (cols - BAND_COLS)·pitch` 本身就已越过标语右缘（`left-12` + display-1 文本宽），`bandsUsed` 仍是 1 ⇒ 大字标语被卡片压住一半，E18 要防的事按原判据照样发生。修法：`WidgetLayer` 把上桌面那些件的外接矩形**同源**写进 `widgetRuntime.usedRect`（与 `bandsUsed` 同一次 `syncPlacement`），`Desktop.vue` 的让位条件改为 `bandsUsed ≥ 2 || 与标语盒子相交`；相交量的是**自己那一块**的 `getBoundingClientRect()`（换语言 / 字体异步到位由 `ResizeObserver` 重测），几何权威仍在宿主层，Desktop 不解析网格——偏差 8 的分工不变，只是多给它一条自己算得出的判据。两条腿钉住（`widget.spec.ts`「标语让位」），且各自带「这一屏的前提确实成立」的前置断言：560×800 时 `card.x < slogan.x + slogan.width` 且标语淡出；1440×900 时 `card.x ≥ slogan.x + slogan.width` 且标语常驻（防过度让位把这条装饰凭空抹掉）。反证实测：条件退回只判 `bandsUsed ≥ 2`，窄那条红（读到的仍是 `opacity-100`）、宽那条绿。`shell-3bands` 的结构断言（`opacity-0`）本轮原位通过，让位口径改动没有把它推离基线口径。同屏实测读数（两张截图取证）：大字标语盒子在两种视口下恒为 `x=48 · w=246 · h=100`（右缘 294），`bandsUsed` **两处都是 1**——这正是原判据漏掉它的原因；摆放域左缘 560×800 下为 192（192 < 294 ⇒ 相交，淡出），1440×900 下为 1072（> 294 ⇒ 不相交，常驻）。 同轮再往这条动线上走一步又抓出一个更早的缺陷：溢出清单的锚点方向错了，处置动作在**所有**视口下都落在屏幕右缘之外（算术、成因与 `right-0` 修法见偏差 25；四条老溢出腿全绿是因为 Playwright 的 `click()` 会把目标滚进视口，用户却没有横向滚动条可滚）。

25. **溢出清单的锚点错了方向：它从出口左缘向右长，三个处置动作在任何视口下都在屏幕右缘之外**（2026-10-06，§4.10）：`#widget-overflow-list` 原本只有 `absolute bottom-full`、不给 `left/right`，静态位置落在容器左缘，而容器按 `right: MARGIN` 贴桌面右缘 ⇒ 清单宽 448（`--container-md`）从 `x = vw − 24 − chip 宽(≈111)` 起**向右**长，恒越界约 313px（560 下实测 `list x=425 w=448`、三个按钮在 `x=744/808/838`；1280 同理）。用户点「+N 个未显示」看到的是一块被屏幕右缘切掉的面板，处置动作全在屏外——`max-w-[calc(100vw-48px)]` 只封顶宽度、不换锚点，救不了它。四条老腿为什么全绿：`toBeVisible()` 只问「渲染了没有」，而 `click()` 会先把目标**滚进视口**——桌面壳层没有可见的横向滚动条，用户滚不到的地方，自动化却滚得到，于是「点得动」被误当成「看得见」。修法：锚点改为贴出口**右缘**向左开（加 `right-0`），与摆放域右锚定同一条方向口径。新增 560×800 那条腿把判据换成 `toBeInViewport({ ratio: 0.9 })`（整行 + 三个动作逐个都要 ≥90% 在视口内），再真点一次「移除」并读回 IDB。反证实测：拿掉 `right-0` ⇒ `1 failed / 5 passed`，只有这条新腿红。由此定一条通用口径：**浮层与弹层的可达性判据用 `toBeInViewport` 而不是 `toBeVisible`，且不要留默认 `ratio: 0`**（部分可见即过，等于免检）。**同一根因按同族扫过一遍**（560×800 / 900×620 / 1280×800 三档实测每个浮层的盒子与其内全部控件的横向越界数）：桌面右键菜单（`x=67/108/154`，宽 176）、卡片菜单（`x=364/704/1084`，宽 176，右缘 540/880/1260 均在屏内——菜单宿主本来就带夹取）、小组件库抽屉（宽 420、右锚 `x=140/480/860`）三处**横向越界控件数为 0、塌陷控件数为 0**；抽屉内一度报出的 32~33 个「不在视口」全部是**纵向**滚出（抽屉自身可滚，属正常），把度量改成只看横向后归零。也就是说这条锚点缺陷只发生在溢出清单这一处浮层上，其余浮层没有同形状的洞。

26. **接语义图标撞上的三道坑：扫描器只认两种字面量形状、`OsIcon` 的静默回落、以及被 prettier 折行过的期望数据源**（2026-10-06，§4.9 图形通道 / 批次 B 的 12 个图标）：
    - **`icons:gen` 的可见性是字面量形状决定的，不是"用没用"决定的**。它只扫 `<OsIcon … name="x">` 与 `icon: 'x'` 两种形状，所以 `icon: online.value ? 'wifi' : 'wifi-off'` 这种 ternary **一个名字都扫不到**：白名单不补，`IconName`（`keyof typeof ICON_MAP`）随即把整块编译拦住——实测读数 `Type '"wifi" | "wifi-off"' is not assignable to type …`。这里类型系统确实兜住了，但兜住的方式是「编译不过」，而**运行时它是无声的**：`OsIcon` 写的是 `ICON_MAP[props.name] ?? ### 附之三：截图与摆放域算术引入的读数（2026-10-06，E17/E18）

> 截图未标视口；本节的数全部来自代码常量与算术，不依赖那张截图的具体尺寸。

- **纵向零间距**：截图（浅色主题 + `wallpaper-sky`）时钟卡与月历卡**边缘直接相接**，中间无壁纸缝。代码依据：`geometry.ts` 行推进三处 `rowY += h`（`:110`、`:125`、`:130`）均未加 `GUTTER`，而横向两处加了（band 间距 `pitch = bandW + gutter` `:87`、两个 sm 并排 `bandLeft + cell + gutter` `:117`）。
- **算术核对**：`sm` 高 `2*68+24=160`，两件纵向相接 ⇒ 第二件 `y=160`＝第一件底边，净间距 0；`md`→`lg` 同理（本例即 160→160）。横向若并排两 sm，第二件 `x=bandLeft+68+24`，净间距 24——**同一份常量，两个方向不一致**，可判为漏写而非取舍。
- **连带影响（按 `gridH = rows*68 + (rows-1)*24` 逐档算过，不是猜的）**：溢出判定 `rowY + span.h > gridH`（`:113`）按无间隙累计，行数上限从 `⌊gridH/h⌋` 变为 `⌊(gridH+24)/(h+24)⌋`。**多数视口两者相同**（rows=5~8、h=160 或 344 时都不变），差异在余量刚好被 gutter 吃掉时才显形——例：rows=9（`gridH=804`，视口高约 984px）时 h=160 的件从 5 行降到 4 行。**但无论件数是否变化，第二行往下的 y 一律 +24、第三行 +48**，所以 `shell-light/dark` 与含多件的 `widget-*` 基线必然全部重生成（G-3、§5 连带门禁）。
- **摆放域与标语重叠的算术（E18）**：1280×800 视口下 `bounds.w=1280`、`cols=⌊(1280−48+24)/92⌋=13`、`gridW=13×68+12×24=1172`、`originX=1280−24−1172=84`；band 宽 344、`pitch=368`，故三个 band 的左缘依次为 912 / 544 / **176**。大字标语左缘 48、5 字 × 48px ≈240 宽 → 右缘 ≈288 > 176，**第三 band 落进标语区**。视觉基线那组（1280×800）今天只有 3 件（1 band，左缘 912）所以没暴露。
